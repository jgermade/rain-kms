# Initial implementation

## 2026-11-25

### Goal

Show a kiosk screen with content like the canvas demo in
`wasm-gaming/engine-specs/demo/canvas-renderer.js` (katakana rain with rainbow
hues), using as little RAM as possible.

### Decisions

- **Native Rust drawing straight to DRM/KMS** instead of a browser kiosk
  (Firefox + cage, estimated 300–500 MB) or a Wayland client inside cage.
  No compositor or display server is involved.
- **Own implementation, not a copy** of the demo: the source repository has no
  licence, so the effect was rewritten from scratch.
- **Default mode 1920×1080** even though the target display is 4K: a 4K scan-out
  buffer is 33 MB (66 MB double-buffered) and software rendering at 4K costs far
  more CPU on the target machine (Alder Lake-N, 4 cores). The display upscales.
- **Glyph cache**: the 96 katakana (U+30A0–U+30FF) are rasterised once with
  `ab_glyph` (lazy parsing, unlike `fontdue`, which preloads every glyph of the
  CJK font); the ~20 MB font file is dropped right after.
- **No read-back from video memory**: glyphs are blended against the known
  background colour, which avoids slow reads from write-combined buffers.
- **Double buffering with page flips** synced to vblank, plus a frame-rate cap
  (default 30 FPS) to save CPU.
- **`--card auto`**: the DRM card index can change between boots.
- **`--capture`**: renders a frame to a PPM file to check the output without a
  display (used during development over SSH).
- The FPS overlay of the original demo was left out: it is a benchmarking aid
  and not useful on a kiosk.

### Measurements (target machine, 1920×1080 @ 60 Hz, 30 FPS)

- Binary: ~450 KB (release, LTO, stripped).
- RSS: ~2.6 MB steady; 22 MB peak during start-up (font load).
- Scan-out buffers: 2 × 8 MB, allocated by the driver.
- CPU: ~17 % of one core.

### Status

- Builds cleanly (`cargo build --release`, `cargo clippy`).
- Tested on the real display over HDMI and with `--capture`.
- `install.sh` and `rain-kms.service` written; **not yet installed** on the
  target machine.

### Open questions

- Hardware-accelerated rendering is not needed at current CPU usage; revisit if
  4K output is required.
- Graceful handling of SIGTERM (currently the kernel releases the display when
  the process exits).

## 2026-11-25 — installed, darker background, CPU work

- Installed on the target machine with `install.sh`; `rain-kms.service` runs as
  the `kiosk` user on tty1. Verified: 1920×1080 @ 60 Hz, RSS ~2.7 MB, no restarts.
  Note: the start-up log line shows with `journalctl _PID=…` / `-t rain-kms`,
  not always with `journalctl -u rain-kms`.
- Background changed from `#060910` to pure black by default; new
  `--background RRGGBB` option.
- Measured ~21 % of one core at 30 FPS, which is too much for this effect.
  Suspected causes: re-mapping each 8 MB dumb buffer every frame (thousands of
  page faults per frame) and clearing the whole 8 MB frame every time
  (~250 MB/s of writes to write-combined memory).
- Changes: both buffers are mapped once for the whole run; each buffer keeps the
  per-column rectangles it last painted, and only those are cleared before
  drawing. Checked with `--capture`: no leftover glyphs.
- `install.sh` now restarts the service, so reinstalling picks up a new binary
  (`enable --now` does not restart a running unit).
- Pending: measure CPU on the display after reinstalling.

## 2026-11-25 — where the CPU goes, cell-based redraw

- After reinstalling with mapped-once buffers and dirty rectangles: 17.5 % of one
  core on the display (20 s average). Barely better.
- Added `--bench` (renders into ordinary RAM): ~1 ms per frame, i.e. ~3 % at
  30 FPS. So most of the cost on the display is writing scattered single pixels
  into the write-combined scan-out buffer, not the drawing maths.
- Composing each column in a RAM tile and copying it row by row: same ~1 ms in
  RAM; display measurement pending.
- Key insight (from the user): glyphs never move. Each one sits in a fixed grid
  cell; only lit/brightness/hue/char change. Now each buffer keeps one u32 key per
  cell (lit, head, char, brightness level out of 63, hue in 6° steps) and only
  cells whose key differs are redrawn: ~580 of 2368 cells per frame. Cells are
  composed from the key alone, so equal keys always give identical pixels in both
  buffers. Hue quantisation is what keeps unchanged cells from being redrawn as
  the rainbow drifts.
- Question raised: does it use the GPU? No — drawing is on the CPU; the GPU's
  display engine only scans the buffers out. GPU rendering (EGL/GBM + GLES via
  Mesa) would cut CPU but load the Mesa driver, adding tens of MB of RAM, which
  goes against the project's main goal.

## 2026-11-25 — the real cause, and integer blending

- With cell-based redraw installed: still 17.3 % on the display. Split by
  user/kernel time: 17.1 % user, 0.5 % kernel, almost no page faults.
- `--bench` extended to render into real scan-out buffers (created and mapped
  without taking the display): they write at ~12.9 GB/s, as fast as RAM, and
  drawing into them costs the same ~3.6 %. So write-combined memory was not the
  problem either; the earlier hypotheses were wrong.
- Real cause: CPU frequency. The governor is `powersave` (EPP
  `balance_performance`, 0.7–3.4 GHz). A paced run (one frame, then sleep, as in
  the service) takes ~4.3 ms per frame instead of ~1.2 ms, because short bursts
  never raise the clock. CPU % is inflated by the low clock; the actual work is
  ~4 % of a core at full speed. Forcing a higher clock would lower the % but
  raise power use, so it was ruled out.
- Integer blending (option chosen by the user): glyphs are now stored as
  cell-sized coverage maps; each redrawn cell builds a 256-entry colour table in
  integer maths and is written straight to the scan-out buffer row by row (one
  lookup per pixel; no tile, no fill + copy). Results: 1.2 → 0.83 ms per frame at
  full speed (−30 %); paced 11–13 % → 10.5–11.7 % CPU time. Output checked with
  `--capture`.
- Remaining options if more is needed: lower FPS (e.g. 20) and coarser hue steps
  (e.g. 12°) to redraw fewer cells.

## 2026-11-25 — final summary

- Installed with integer blending: **12.5 % of one core** on the display
  (12.1 % user, 0.5 % kernel, 30 s average), down from 17.3 %; RSS ~2.8 MB.
- Decided to stop here: lower FPS and coarser hue steps were offered but not
  applied; GPU rendering was ruled out because it would add tens of MB of RAM.
- State at close: renderer with per-cell redraw and integer blend tables,
  `--background`, `--bench` (RAM, scan-out buffers and paced runs), `--capture`;
  `install.sh` restarts the service on reinstall; README updated with the final
  measurements.
- Follow-up ideas (not started): graceful SIGTERM handling, colour/speed options,
  `--fps 20` and a configurable hue step for lower CPU.
